# Этап 2. Обработка потока

> **Статус:** утверждена автором 2026-11-02 · **Срок:** 2 недели (бриф: недели 2–3) · **Бриф:** §10 «Этап 2», §6.3–6.4 · **Milestone:** `Stage 2 — Stream processing`

## Цель
Превратить поток позиций `positions.raw` в факты о движении: где машина на маршруте, когда она прибыла на остановку и уехала, насколько опаздывает, не слиплась ли с соседней. Без потерь и без дублей на выходе при рестарте Processor.

Этап делается на **Хельсинки** (самый частый и богатый поток); Берген и Бостон подключаются к обработке в этапе 4 — без изменений Processor, только конфигурацией. Импортёр расписаний с первого дня проверяется на снимках всех трёх городов.

**Закрываемые цели брифа:** C4 (нет потерь и дублей при рестарте — тест), C3 (основа задержки до карты: lag Processor около нуля), C9 (unit-тесты на реальных треках, интеграционные, replay-тест), C10 (ADR 1, 3, 4), C5 (метки «фактическое время прибытия» для обучения).

## Архитектура этапа (кратко)
```
GTFS-снимки (архив сервера) ─► Worker: GtfsImporter ─► Postgres: gtfs.* (версия снимка на фид, атомарное переключение)
                                                                │ активные дни службы (сегодня ± 1)
positions.raw ──► Processor (consumer group) ──────────────────┘
                   │ состояние машины в памяти: трек, рейс, дистанция вдоль shape, последняя остановка
                   │ снапшот состояния + offset'ы ─► Redis
                   ├─► positions.enriched   (ключ {FeedId}/{VehicleId})
                   ├─► events.stop          (ключ routeId; id события детерминирован)
                   ├─► events.anomaly       (слипание)
                   └─► *.dlq                (необрабатываемое после N попыток)
events.stop ──► Worker: StopEventSink ─► Postgres stop_events (upsert по id события) ← идемпотентный приёмник
```
- **At-least-once**: Processor фиксирует offset только после того, как снапшот состояния записан; после рестарта он читает снапшот и повторяет сообщения с этого offset'а. Повторные события имеют тот же id и схлопываются upsert'ом у приёмника. Kafka-транзакции не используем (ADR 4).
- Сырые данные не фильтруются: `positions.raw` и архив хранят всё, а неправдоподобные точки (скачки координат) отсекает Processor с причиной в метриках.

### 2.3 Импорт GTFS в Postgres (#41)
- [x] Схема `gtfs.*` с версией снимка на фид; массовая загрузка через `COPY` (Npgsql binary import); переключение на новую версию одной транзакцией, старая удаляется после.
  - Версия = LIST-партиция по `snapshot_id`: `COPY` в отдельную таблицу без индексов → PK → `ATTACH` (читатели не блокируются) → `is_active`; старая версия — `DROP` партиций отдельной транзакцией, только если `LOCK TABLE … NOWAIT` взял все 7 родителей (иначе — следующий импорт). Тот же файл (SHA-256) не перечитывается, ещё не удалённая старая версия снова активируется; битый снимок или повтор ключа → откат, прежнее расписание остаётся (ADR-0008).
- [x] Новый проект `TransitPulse.Worker`: импорт по расписанию (раз в сутки) из папки снимков; Worker и его миграции — в AppHost.
  - Берёт самый свежий законченный снимок фида (есть `.zip.sha256`); ошибка одного фида не мешает остальным; отвергнутый файл не перечитывается до нового.
- [x] Схема БД: решение автора 2026-11-02 — SQL-скрипты со своим раннером (`SchemaMigrator`, advisory lock), не EF Core migrations (ADR-0008).

**Готово, когда:** интеграционный тест (Testcontainers) импортирует фикстурный снимок и повторный импорт того же снимка ничего не меняет; импорт реального снимка HSL — время и размер в БД записаны.
- ✅ 2026-11-02: 14 тестов на `timescaledb-ha` (в т. ч. повторный импорт → `Unchanged`, читатель не блокирует импорт; после ревью — битая строка посреди `COPY`, только `calendar_dates`, возврат старого файла, сервис Worker); HSL 31.10 — 131 с, 1 507 МБ; Entur 74 с, MBTA 28 с (`docs/benchmarks.md`, «GTFS import»).

## ADR этапа
- ADR-0009 (ADR 1 брифа) — Modular monolith with four deployable units (Worker появился в 2.3; ADR — в 2.4 вместе с Processor, решение автора 2026-11-02).
- ADR-0010 (ADR 3 брифа) — Key positions by vehicle and process them in one loop (задача 2.4).
- ADR 4 — At-least-once with idempotent receivers instead of exactly-once: снапшот + offset, детерминированные id, upsert (задача 2.10).
- ADR-0008 — Store GTFS snapshots as partitions, with plain SQL migrations (задача 2.3).

## Решения, принятые в этой спецификации (утверждены 2026-11-02)
1. **Processor этапа 2 — только Хельсинки**, импортёр расписаний — сразу для трёх городов (только разбор и загрузка). Так по брифу (этап 4), а общий импортёр проверяется на разных снимках с первого дня.
2. **Новый фид `hsl-stop` (2.1)** — эталонные события HSL для приёмки детекции и для меток C5. Деньги не нужны; нагрузка на сборщик — по замеру. Без него приёмка «совпадают с проверкой» остаётся ручной на 20–50 событиях.
3. **Расписания живут в Postgres** (версия снимка на фид), Processor загружает в память только активные дни. Альтернатива — Processor читает zip сам: меньше движущихся частей, но 940 МБ `stop_times` на каждом старте и нет общего справочника для API (этап 3).
4. **Worker появляется в этапе 2**: импорт GTFS и идемпотентный приёмник `events.stop`. Без приёмника «нет дублей» доказать нечем — в топике повторы при at-least-once ожидаемы.
5. **Восстановление — снапшот в Redis + offset'ы**, а не перечитывание топика с начала: `positions.raw` хранится 24 ч, перечитывать его на каждом рестарте долго.
6. **Фильтр правдоподобия — в Processor**, не в Ingestor: архив и `positions.raw` остаются «как пришло», правила можно менять и переигрывать.
7. **Эталон replay-теста — маленький срез в репозитории** (одна-две линии, ~1 ч, единицы МБ), чтобы тест шёл в CI; полный час архива — локальный прогон, результат в `docs/benchmarks.md`.
8. **Пороги приёмки детекции и слипания** утверждаются автором по первому замеру, а не выдумываются заранее.
