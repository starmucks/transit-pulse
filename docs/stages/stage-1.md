# Этап 1. Сбор данных трёх городов

> **Статус:** утверждена автором 2026-10-15 · **Срок:** 1–1,5 недели · **Бриф:** §10 «Этап 1» · **Milestone:** `Stage 1 — Data collection`

## Цель
Как можно раньше начать круглосуточно копить историю трёх городов на сервере фазы A, затем — привести три разных формата и протокола к единой модели `VehiclePosition` и публиковать её в `positions.raw`.

**Закрываемые цели брифа:** C2a (три формата/протокола → одна модель), C5 (история для обучения и официальные прогнозы для сравнения), C1 (Native AOT, `TimeProvider`, `BackgroundService`), начало C2 (замер живого потока), C9 (контрактные тесты).

## Архитектура этапа (кратко)
```
IFeedSource ──► Channel<RawRecord> (bounded) ──► ArchiveSink (Parquet+zstd, по часам)   ← всегда
   (MQTT / HTTP poll)                         └► Normalizer ► Channel<VehiclePosition> ► KafkaSink (positions.raw) ← только локально
```
- Один процесс **Ingestor**, два режима конфигурацией: `archive` (сервер фазы A, без Kafka) и `full` (локально в Aspire).
- Сырьё хранится **как получено** (payload + время приёма + метаданные), чтобы нормализацию можно было переиграть по архиву после исправления багов.

## Задачи
Порядок: сначала то, что запускает сбор (1.1–1.3), потом нормализация (1.4–1.7), потом инструменты (1.8–1.9).

### 1.1 Каркас Ingestor и архив сырья (#13)
- [ ] `TransitPulse.Ingestor` (Worker SDK, Native AOT), `TransitPulse.ServiceDefaults` (OpenTelemetry, health checks), `tests/TransitPulse.Ingestor.Tests`.
- [ ] `RawRecord` (feed, received at, payload bytes, метаданные), `IFeedSource`, ограниченный `Channel<T>` между источником и записью.
- [ ] `ArchiveSink`: Parquet + zstd, файл на час и фид, row group сбрасывается по размеру/времени (весь час в памяти не держим — 1 ГБ RAM), атомарное закрытие файла (`.tmp` → rename).
- [ ] Ingestor в AppHost.

**Готово, когда:** юнит-тесты на ротацию по часам и запись/чтение Parquet зелёные; `dotnet publish -r linux-x64 -p:PublishAot=true` проходит без AOT-предупреждений.

### 1.2 Сырые источники: HSL MQTT и опрос HTTP-фидов (#14)
- [ ] `HslMqttRawSource`: MQTT over TLS `mqtt.hsl.fi:8883`, `/hfp/v2/journey/ongoing/vp/#`, переподключение.
- [ ] `HttpPollingRawSource` — один класс, фиды задаются конфигурацией (URL, интервал, заголовки, `ETag`/`If-Modified-Since`, постоянный `requestorId` для SIRI):
  - Entur: SIRI-VM (10–30 с), SIRI-ET, SIRI-SX — инкрементально через `requestorId`;
  - MBTA: VehiclePositions, TripUpdates (60 с), Alerts (при изменении);
  - HSL: TripUpdates (60 с), Alerts (при изменении);
  - Open-Meteo: погода трёх городов (раз в час).
- [ ] Заголовки `ET-Client-Name` / `Digitraffic-User` — из конфигурации ([data-sources](../data-sources.md)).

**Готово, когда:** локально за час набираются файлы по всем фидам; замерен объём в сутки по фидам (оценка для диска 10 ГБ); неизменённые снимки не пишутся повторно.

### 1.3 Запуск сборщика на сервере 24/7 (#15)
- [ ] `deploy/collector/`: systemd-юнит (автоперезапуск, лимит памяти), скрипт публикации AOT-бинарника, политика хранения (удаляем только то, что уже выгружено в облачный буфер).
- [ ] Выгрузка: сервер → облачный буфер (по таймеру, несколько раз в сутки) → локальный архив на ПК (ежедневно, по расписанию).
- [ ] `deploy/collector/health.sh`: диск, свежесть последнего файла по каждому фиду, размер за сутки; предупреждение при диске > 80 %.
- [ ] Команды на сервере выполняет автор (или явно разрешает ассистенту).

**Готово, когда:** сбор идёт на сервере ≥ 24 ч без пропусков > 5 мин по фиду; файлы дошли до локального архива; health-скрипт показывает зелёное.

### 1.8 Надёжность и метрики источников (#20)

### 1.9 Replay и профиль потока (#21)
- [ ] Режим `replay`: читает архив за период и прогоняет через тот же конвейер с множителем ×1…×50 (`TimeProvider`).
- [ ] Команда `stats`: сообщений/с по фидам по часам суток из архива → `docs/benchmarks.md` («Суточный профиль потока»).

**Готово, когда:** replay записанного часа даёт то же число позиций, что живой поток за этот час (± дубли, которые отсекает дедуп); ×10 работает; профиль за 24 ч опубликован.

## Критерии приёмки этапа (бриф §10)
- [ ] На сервере круглосуточно копится история трёх городов (сырьё + прогнозы, объявления, погода): ≥ 48 ч подряд без пропусков > 5 мин по любому фиду (`health.sh`).
- [ ] Все три адаптера пишут в `positions.raw` единую модель: локально в Aspire видны позиции `hsl`, `entur-sky`, `mbta`.
- [ ] Замерен суточный профиль потока по каждому городу (`docs/benchmarks.md`).
- [ ] Replay воспроизводит записанный час (тест/команда с совпадающим числом позиций).
- [ ] Контрактные тесты JSON, XML, protobuf зелёные в CI.

## ADR этапа
- ADR-0003 — Unified `VehiclePosition` model and feed adapter pattern (бриф §8 п. 6; в брифе — этап 2, но решение принимается здесь).
- ADR-0004 — Phase-A collector: Native AOT + systemd, raw archive in Parquet+zstd (почему не Docker на диске 10 ГБ; почему сырьё, а не нормализованные данные).
- ADR 6a (push vs pull) — по брифу этап 4; черновик можно начать после 1.7, когда все три протокола реализованы.

## Решения, принятые в этой спецификации (проверьте)
1. **Native AOT + systemd** на сервере, не Docker: меньше RAM/диска, нет демона; Docker остаётся для фазы B (compose).
2. **Сырьё как получено**, а не нормализованные данные: ошибку нормализатора можно исправить и переиграть архив. Сжатие zstd + Parquet даёт компактность с первого дня.
3. **Вспомогательные фиды (прогнозы, объявления, погода) — сразу в 1.2**, а не в «дни 5–7»: это тот же HTTP-опрос конфигурацией, а прогнозы нужны для сравнения в C5 за тот же период, что и позиции.
4. **Один `HttpPollingRawSource` на все pull-фиды**; различия форматов — только в нормализаторах (1.5–1.7).
5. **Infrastructure-проект пока не создаём:** Parquet и Kafka-код живут в Ingestor и выносятся в `TransitPulse.Infrastructure` на этапе 2, когда появится второй потребитель (Processor/Worker).
6. **Replay — режим Ingestor**, а не отдельный сервис (четыре деплоймент-единицы).
7. **`tests/TransitPulse.Ingestor.Tests`** — новый тестовый проект для адаптеров (в брифе §9 его нет, но контрактные тесты адаптеров не доменные).

## Риски
| Риск | Мера |
|---|---|
| Библиотеки (MQTT, Parquet, Kafka) несовместимы с Native AOT | Проверить в 1.1 первым шагом; запасной вариант — self-contained single-file без AOT (ADR-0004 фиксирует) |
| 1 ГБ RAM: буфер Parquet переполняет память | Row group сбрасывается по размеру (порядка десятков МБ), лимит памяти в systemd, метрика памяти |
| Диск 10 ГБ заполняется, если выгрузка сломалась | Удаление только выгруженного + аварийное удаление самого старого при > 90 %; предупреждение > 80 % |
| Entur истекает/сбрасывает `requestorId` | Детект полного снимка, восстановление состояния; контрактный тест |
| Сбор стартует поздно из-за 1.1–1.2 | Таймбокс: сбор на сервере к концу 3-го дня; нормализация может ждать, сырьё — нет |
| Изменение формата источника | Сырьё в архиве + контрактные тесты на реальных ответах |

## Новые концепции этапа
MQTT (QoS, сессии, TLS), `BackgroundService` и `IHostedService`, `Channel<T>` и backpressure, Parquet (колоночный формат, row groups, zstd), Native AOT и trimming, systemd-юниты, потоковый `XmlReader`, ISO 8601 duration, protobuf и GTFS-RT, условные HTTP-запросы (`ETag`), Polly, идемпотентный Kafka-продюсер и батчинг, метрики OpenTelemetry, `TimeProvider` для replay.
