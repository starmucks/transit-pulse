# Этап 1. Сбор данных трёх городов

> **Статус:** утверждена автором 2026-10-15 · **Срок:** 1–1,5 недели · **Бриф:** §10 «Этап 1» · **Milestone:** `Stage 1 — Data collection`

## Цель
Как можно раньше начать круглосуточно копить историю трёх городов на сервере фазы A, затем — привести три разных формата и протокола к единой модели `VehiclePosition` и публиковать её в `positions.raw`.

**Закрываемые цели брифа:** C2a (три формата/протокола → одна модель), C5 (история для обучения и официальные прогнозы для сравнения), C1 (Native AOT, `TimeProvider`, `BackgroundService`), начало C2 (замер живого потока), C9 (контрактные тесты).

## Архитектура этапа (кратко)
```
IFeedSource ──► Channel<RawRecord> (bounded, ждёт) ──► ArchiveSink (Parquet+zstd, по часам)        ← всегда
   (MQTT / HTTP poll)                                └► NormalizingSink: Channel<RawRecord> (bounded, отбрасывает)
                                                         ► PositionRouter (нормализатор города + дедуп) ► KafkaSink (positions.raw) ← режим full
```
- Ответвление в нормализацию отбрасывает записи при переполнении, а не тормозит архив; дыры в `positions.raw` закрываются replay ([ADR-0005](../adr/0005-drop-positions-under-backpressure-and-rebuild-them-from-the-raw-archive.md)).
- Один процесс **Ingestor**, два режима конфигурацией: `archive` (сервер фазы A, без Kafka) и `full` (локально в Aspire).
- Сырьё хранится **как получено** (payload + время приёма + метаданные), чтобы нормализацию можно было переиграть по архиву после исправления багов.

### 1.3 Запуск сборщика на сервере 24/7 (#15)
- [x] `deploy/collector/`: systemd-юнит (автоперезапуск, лимит памяти), скрипт публикации AOT-бинарника, политика хранения (удаляем только то, что уже выгружено в облачный буфер).
- [x] Выгрузка сервер → облачный буфер: по таймеру каждый час, только закрытые файлы; на сервере файл удаляется после подтверждённой выгрузки (сервер держит не больше 1–2 суток).
- [x] Выгрузка облачный буфер → локальный архив: скрипт на ПК **запускает автор вручную** (ПК включается примерно раз в 3 дня); скрипт забирает всё накопленное. Буфер рассчитан минимум на 10 дней.
- [x] Защита от одновременной работы (скрипт на ПК не должен читать то, что сервер ещё пишет):
  - сервер выгружает файл под временным именем (`*.partial`) и переименовывает после завершения; ПК видит только готовые файлы;
  - на время выгрузки сервер кладёт в буфер метку `upload.lock` (с временем начала); скрипт на ПК при метке ждёт её снятия или выходит с понятным сообщением; метка старше 2 ч считается зависшей;
  - локальная блокировка не даёт запустить два экземпляра скрипта на ПК;
  - рядом с каждым файлом сервер кладёт контрольную сумму; ПК сверяет её и только потом удаляет файл из буфера. Скачивание идемпотентное: повторный запуск не дублирует файлы.
  - Реализация: контрольная сумма — SHA-256, который сообщает API облака (отдельный файл не нужен); скрипт на ПК — локальный инструмент автора, в репозиторий не входит. ✅ 2026-10-21: забор запущен через 5 с после начала выгрузки сервера — ждал метку 10 мин и вышел, не взяв ни одного файла; недогруженный `.partial` в буфере пропущен.
- [x] Выгрузка не мешает сборщику: пауза в часы пик (по замеру CPU), лимит скорости, `CPUQuota=20%`; сборщику `CPUWeight=1000` (после инцидента 2026-10-21).
- [x] `deploy/collector/health.sh`: диск, свежесть последнего файла по каждому фиду, размер за сутки; предупреждение при диске > 80 %.
  - Свежесть — по наличию файла текущего часа (у тихих фидов `.tmp` пишется только при сбросе row group), у HSL — по времени изменения; плюс рестарты, память, сироты `.tmp`, ошибки за час. Заполнение облачного буфера скрипт не видит: токен без доступа к квоте.
  - ⚠️ 2026-10-19/20: 102 OOM-рестарта за 40 ч незамечены (см. STATUS) — критерий «≥ 24 ч без пропусков» отсчитывается заново с 2026-10-20 18:53 UTC.
- [x] Команды на сервере выполняет автор (или явно разрешает ассистенту).

⚠️ 2026-10-21: замер в будний день — 1 vCPU мало (`cpu.pressure full` 41–61 %); сбор на этом сервере остановлен 10:24 UTC, данные выгружены, переезд на сервер 2 vCPU / 2 ГБ / 500 ГБ HDD (решение автора; сбор с 2026-10-21 19:15 UTC, архив хранится на сервере, ПК копирует по SSH). Критерии 1.3 проверяются заново на новом сервере; облачный буфер больше не используется.

- [x] Копия на ПК по SSH (с 2026-10-21, вместо облачного буфера): ПК берёт только закрытые `*.parquet` и снимки GTFS с готовым `.zip.sha256`, сверяет SHA-256, на сервере ничего не удаляет; повторный запуск пропускает скопированное. ## Решения, принятые в этой спецификации (проверьте)
1. **Native AOT + systemd** на сервере, не Docker: меньше RAM/диска, нет демона; Docker остаётся для фазы B (compose).
2. **Сырьё как получено**, а не нормализованные данные: ошибку нормализатора можно исправить и переиграть архив. Сжатие zstd + Parquet даёт компактность с первого дня.
3. **Вспомогательные фиды (прогнозы, объявления, погода) — сразу в 1.2**, а не в «дни 5–7»: это тот же HTTP-опрос конфигурацией, а прогнозы нужны для сравнения в C5 за тот же период, что и позиции.
4. **Один `HttpPollingSource` на все pull-фиды**; различия форматов — только в нормализаторах (1.5–1.7).
5. **Infrastructure-проект пока не создаём:** Parquet и Kafka-код живут в Ingestor и выносятся в `TransitPulse.Infrastructure` на этапе 2, когда появится второй потребитель (Processor/Worker).
6. **Replay — режим Ingestor**, а не отдельный сервис (четыре деплоймент-единицы).
7. **`tests/TransitPulse.Ingestor.Tests`** — новый тестовый проект для адаптеров (в брифе §9 его нет, но контрактные тесты адаптеров не доменные).

## Риски
| Риск | Мера |
|---|---|
| Библиотеки (MQTT, Parquet, Kafka) несовместимы с Native AOT | Проверить в 1.1 первым шагом; запасной вариант — self-contained single-file без AOT (ADR-0003 фиксирует) |
| 1 ГБ RAM: буфер Parquet переполняет память | Row group сбрасывается по размеру (порядка десятков МБ), лимит памяти в systemd, метрика памяти |
| Диск 10 ГБ заполняется, если выгрузка сломалась | Удаление только выгруженного + аварийное удаление самого старого при > 90 %; предупреждение > 80 % |
| Entur истекает/сбрасывает `requestorId` | Детект полного снимка, восстановление состояния; контрактный тест |
| Сбор стартует поздно из-за 1.1–1.2 | Таймбокс: сбор на сервере к концу 3-го дня; нормализация может ждать, сырьё — нет |
| ПК долго не включается, облачный буфер переполняется | Буфер ≥ 10 дней при замеренном объёме; `health.sh` показывает заполнение буфера и время последнего забора на ПК; предупреждение > 80 % буфера |
| Изменение формата источника | Сырьё в архиве + контрактные тесты на реальных ответах |
