# Этап 4. Все три города в продукте

> **Статус:** утверждена автором 2026-11-27 · **Срок:** ~3–4 дня (бриф: неделя 5) · **Бриф:** §10 «Этап 4», §2.2 C2a · **Milestone:** `Stage 4 — All three cities`

## Цель

Показать, что адаптерная архитектура работает: Берген и Бостон проходят тот же Processor/API/карту, что и Хельсинки, **без правок ядра** — только конфигурация, расписания и адаптеры. Переключатель городов на карте; сводка пунктуальности по городам.

**Закрываемые цели брифа:** C2a (доказательство адаптеров). Опирается на этапы 2–3 (HSL end-to-end).

Уже есть: Ingestor-адаптеры Entur/MBTA → `positions.raw`; GTFS-импортёр (HSL); Processor/карта на `hsl`. Нет: расписания Bergen/Boston в том же импортёре; Processor schedule/delay для этих фидов; city switcher / сравнение на UI.

## Архитектура этапа (кратко)

```
Entur / MBTA GTFS snapshots ──► Worker GtfsImport (тот же пайплайн)
positions.raw (все фиды)     ──► Processor (feed-scoped schedule + matching)
Redis GEO / Timescale        ──► API (feedId в путях уже есть)
web/                         ──► переключатель города + punctuality по городам
```

- Ядро Processor/API не ветвится «if city == …» в бизнес-логике: различия — в адаптерах, конфиге `Schedule:FeedId` / TZ / service date и данных GTFS.
- Четвёртый город (Нидерланды) и ADR push vs pull — **опционально**, не блокер приёмки трёх городов.

## Задачи

### 4.1 GTFS Бергена и Бостона в том же импортёре (#102)
- [ ] Снимки Entur (Bergen/Skyss) и MBTA в раскладке `{feed}/{stamp}.zip` + `.sha256`, как у HSL.
- [ ] Импорт через существующий `GtfsImporter` / Worker без форка пайплайна; при дырах Entur GTFS — зафиксировать, нужен ли NeTEx (отдельное решение/ADR).
- [ ] Проверка: маршруты/остановки читаются API `GET /api/v1/feeds/{feed}/…` для `entur-sky` (или канонический feed id) и `mbta`.

**Готово, когда:** на Aspire после импорта каталог обоих городов непустой; тест или ручная сверка количества routes/stops записана в PR.

### 4.2 Processor для Бергена и Бостона (#103)
- [ ] Конфиг/мультифид: trip lookup, map matching, stop events, delay (у MBTA — из расписания, т.к. TU без delay), bunching — на тех же модулях, что HSL.
- [ ] Регрессия на коротком срезе или контрактной выборке: stop events / delay согласуются с официальными данными «в разумных пределах» (метод в PR).
- [ ] Метрики и consumer groups не ломают HSL-путь.

**Готово, когда:** для каждого из двух городов есть измеренный прогон (replay или live) с ненулевыми enriched positions и хотя бы одним классом stop events; отличия от HSL задокументированы.

### 4.3 Переключатель городов на карте (#104)
- [ ] UI: выбор города/feed → SignalR `Subscribe` с нужным `feedId`, центровка viewport, атрибуция источника.
- [ ] Состояния загрузки/пусто/ошибка; HSL-путь не регрессирует.

**Готово, когда:** локально за ≤ 2 минуты можно переключить Helsinki ↔ Bergen ↔ Boston и увидеть машины (или честное «нет данных» на пустом окне).

### 4.4 Пунктуальность по городам и сравнение (#105)
- [ ] Экран/панель: punctuality (или эквивалент из CAGG/REST) по выбранному городу; простое сравнение городов на одном дашборде.
- [ ] Без новых сервисов; только API + `web/`.

**Готово, когда:** демо-сценарий «три города: карта + punctuality» проходит локально; цифры только из реальных запросов.

### 4.5 Опционально: 4-й город + ADR push vs pull (#106)
- [ ] Отложено до стабильных трёх городов; при старте — ADR 6a (push vs pull) и адаптер Нидерландов.

**Готово, когда:** (если берём в этап) ADR Accepted и на карте виден 4-й feed; иначе issue переносится.

## Критерии приёмки этапа (бриф §10)

- [ ] Три города на карте и дашборде **без изменений Processor/API, кроме конфигурации и адаптеров**.
- [ ] На выборке задержки и прибытия в Бергене и Бостоне согласуются с официальными данными в разумных пределах (метод и окно в benchmarks или PR).
- [ ] C2a: новый город = адаптер + конфиг + GTFS, без переписывания ядра.

## ADR этапа

- Ожидаемый: **ADR 6a** push vs pull для 4-го города — только если делаем задачу 4.5.
- Иначе новых ADR не требуется, если хватает ADR-0006 / существующего GTFS-импорта.

## Решения (утверждены 2026-11-27)

1. Сначала **три города** (HSL, Entur Bergen, MBTA); 4-й город не блокер.
2. Публичный demo-хост (#101) **параллелен** этапу 4, не блокирует C2a.
3. NeTEx для Entur — только если GTFS-выгрузка недостаточна (решение после 4.1).

## Риски

| Риск | Мера |
|---|---|
| GTFS Entur неполон для Bergen | Проверка на 4.1; NeTEx или урезанный scope |
| MBTA delay только из расписания | Уже известно с этапа 1; явно в UI/доках |
| Processor всё ещё singleton (bunching) | Не масштабируем на 3 города в одном процессе без ADR-0013; для демо — отдельные group/конфиг или один процесс с тремя фидами по ёмкости |
| Мало live-данных на Aspire | Replay golden / короткий archive slice на город |
