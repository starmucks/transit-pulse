## 0. Инструкция для ассистента в новом чате

Прочитай документ целиком перед первой задачей. Ключевые правила:

1. **Цели важнее фич.** Каждое решение оценивай вопросом: «Это приближает к целям раздела 2 и проверяемо замером?» Если фича красивая, но ничего не доказывает — она в конце очереди.
2. **Работаем по этапам из раздела 10.** У каждого этапа есть результат и критерии приёмки. Не перескакивай этапы без явной просьбы.
3. **Сбор данных запускается первым** (этап 1) и не останавливается: история нужна для обучения ML-модели, каждый потерянный день — минус день выборки.
4. **Процесс как в команде** (раздел 11): ветки, PR с описанием, зелёный CI, ADR на значимые решения, понятные коммиты. Это часть цели, а не формальность.
5. **Не плодить микросервисы.** Четыре деплоймент-единицы, модульный монолит внутри (раздел 6.1). Новый сервис — только с записанным обоснованием в ADR.
6. **Честность цифр.** Метрики в README — только измеренные. Никаких выдуманных «обрабатывает миллион событий».
8. **Маленькие шаги (раздел 11.2).** Перед кодом — план, изменения небольшими ревьюируемыми порциями. Не генерируй большие объёмы кода за один шаг.
9. **Экономия инфраструктуры (раздел 5.1).** Любое решение, увеличивающее стоимость VPS или внешних сервисов, — только с явным обоснованием и согласием автора.
7. Язык общения — русский. Код, коммиты, README, ADR — на английском (публичный репозиторий для международной аудитории); русская версия README — отдельным файлом.

## 1. Контекст

Transit Pulse — пет-проект: система мониторинга городского транспорта в реальном времени на открытых данных Хельсинки, Бергена и Бостона. Ведётся одним разработчиком с ИИ-ассистентом (Claude Code).

## 2. Цели проекта

### 2.1. Главная цель

> **Построить работающую систему мониторинга транспорта в реальном времени на открытых данных и одном недорогом сервере, в которой каждое инженерное утверждение — пропускная способность, задержка, надёжность, точность прогноза — подтверждено замером.**

### 2.2. Измеримые цели

| ID | Цель | Критерий достижения |
|---|---|---|
| C1 | Современный .NET | .NET 10 (LTS), C# 14; актуальные возможности платформы (Minimal APIs, Native AOT, `HybridCache`, `TimeProvider`) |

### 2.3. Продуктовая цель (вторичная, но обязательная)

Сделать сервис, которым реально можно пользоваться: живая карта, честный прогноз прибытия, понятное объяснение задержек, уведомления в Telegram.

### 2.4. Не цели (сознательно не делаем)

- Мобильное приложение (веб + Telegram-бот достаточно).
- Покрытие всех городов мира (3 города с разными форматами доказывают архитектуру, дальше — «добавляется адаптером»).
- Монетизация, регистрация пользователей сложнее входа через Telegram.
- Собственная картографическая подложка (используем готовые тайлы).
- Идеальная ML-модель: цель — измеримое улучшение и честный MLOps-минимум, а не рекорд.
- Микросервисы «по учебнику» ради количества.

### 2.5. Ограничения

- **Бюджет — минимальный** (подробно §5.1): на этапе разработки — самый дешёвый VPS только под сбор данных, полный стек — локально; на период поиска работы — один VPS ~4 ГБ RAM. Бесплатные источники данных, обучение ML — на локальном ПК, расходы на LLM ограничены дневным бюджетом.
- Время: ~8–10 недель до полной версии, **первое живое демо — к концу 4-й недели**.
- Работа ведётся одним человеком с ИИ-ассистентом.

## 3. Продукт простыми словами

На табло написано «автобус через 3 минуты», через 3 минуты — «через 5», потом он исчезает. Или 20 минут нет ни одного автобуса, а потом приходят три подряд. **Transit Pulse** в реальном времени следит за всем транспортом города, понимает, что происходит на самом деле, честно прогнозирует прибытие и объясняет причины задержек.

**Для пассажира:**
- Живая карта: весь транспорт движется в реальном времени, видно опаздывающих.
- Честный прогноз прибытия (ML), а не прыгающие цифры.
- Помощник в Telegram: «Когда будет 55-й у моей остановки?», «Почему девятый трамвай опаздывает?» — ответ по реальным данным.
- Уведомления: «по будням с 8 до 9 предупреди, если мой автобус опаздывает больше чем на 5 минут».

**Для того, кто управляет транспортом:**
- Пунктуальность каждой линии: где, когда, насколько.
- «Слипшиеся» автобусы в момент, когда это происходит.
- Инциденты на карте: если на участке разом опаздывают несколько маршрутов — вероятно ДТП или затор; система отмечает место и пишет объяснение.
- Ежедневный отчёт.

**Где ИИ:**
1. **Учится предсказывать** прибытие на собственной истории поездок; точность проверяется цифрами.
2. **Объясняет и разговаривает**: отвечает на вопросы и пишет сводки, факты берёт только из системы.

## 4. Источники данных

### 4.0. Выбранные города (решение)

Проект работает с **тремя городами с разными форматами и протоколами**. Выбор обоснован двумя целями: (1) проверка архитектуры — три принципиально разных способа получения данных, приведённых к одной модели; (2) богатые данные — во всех трёх есть позиции, задержки, загруженность и **официальные прогнозы для сравнения с ML** (цель C5).

| | **Хельсинки (HSL)** | **Берген (Entur / Skyss, Норвегия)** | **Бостон (MBTA)** |
|---|---|---|---|
| Формат | Собственный JSON | **SIRI-VM, XML** (европейский стандарт) | **GTFS-Realtime, protobuf** (мировой стандарт) |
| Доставка | **Push**: MQTT-подписка | **Инкрементальный pull**: опрос с `requestorId`, в ответе только изменения | **Полный pull**: опрос снимка |
| Объём (замер) | ~750 сообщ./с вечером, 519 машин | 422 машины Бергена (вся Норвегия ~1 500) | 514 машин вечером (днём ~800) |
| Частота | 1 раз/с на машину | опрос раз в 10–30 с | фид обновляется каждые несколько секунд |
| Задержка в данных | ✅ поле `dl` | ✅ у 100% машин (`PT5M43S`) | ❌ пересчёт по расписанию (в Trip Updates MBTA только абсолютные прогнозы, без `delay`) |
| Загруженность | ✅ `occu` | ✅ у 81% | ✅ у 72% (+ по вагонам у поездов) |
| Особые поля | двери, одометр, скорость | «в пробке» (`InCongestion`) у 86%, «стоит на остановке» | статус у остановки, загрузка вагонов |
| Официальные прогнозы | ✅ GTFS-RT Trip Updates | ✅ SIRI-ET | ✅ GTFS-RT Trip Updates (1 232 рейса) |
| Объявления о сбоях | ✅ GTFS-RT Alerts (fi/sv/en) | ✅ SIRI-SX | ✅ GTFS-RT Alerts (159) |
| Расписание | GTFS (HSL) | NeTEx/GTFS (Entur) | GTFS (MBTA) |
| Ключ | не нужен | не нужен, обязателен заголовок `ET-Client-Name` | не нужен (бесплатный ключ повышает лимиты) |
| Часовой пояс | UTC+2/+3 | UTC+1/+2 | UTC−5/−4 |

**Почему не другие:** Нидерланды (OVapi) — больше машин (~1 700), но поля беднее (нет загруженности и курса), оставлены как запасной GTFS-RT. Осло (Ruter) — позиции через Entur не публикуются.

**Бонус разных часовых поясов:** часы пик приходятся на разное время, поэтому суммарный поток почти круглосуточный — больше реальной нагрузки и данных.

### 4.1. Основные (проверены вживую)

| Источник | Формат / доступ | Измерено | Роль |
|---|---|---|---|
| **HSL High-Frequency Positioning** (Хельсинки) | MQTT over TLS, `mqtt.hsl.fi:8883`, топик `/hfp/v2/journey/ongoing/vp/#`, без ключа | **~750 сообщ./с** в 22:00 (днём больше), 519 машин; режимы: bus, tram, train, metro, ferry | **Основной поток.** Позиция раз в секунду на машину |
| **HSL GTFS static** | ZIP, `https://infopalvelut.storage.hsldev.com/gtfs/hsl.zip` | 78 МБ; `stop_times.txt` ≈ 940 МБ распакованный, `shapes.txt` 22 МБ | Маршруты, остановки, геометрия, расписание |
| **HSL GTFS-RT Trip Updates** | protobuf, `https://realtime.hsl.fi/realtime/trip-updates/v2/hsl` | 597 рейсов | **Официальный прогноз HSL — эталон для сравнения нашей ML-модели (цель C5)** |
| **HSL GTFS-RT Service Alerts** | protobuf, `https://realtime.hsl.fi/realtime/service-alerts/v2/hsl` | 44 активных, тексты на fi/sv/en | Объяснение задержек, контекст для LLM |
| **Entur SIRI-VM** (Норвегия, Берген) | XML, `GET https://api.entur.io/realtime/v1/rest/vm?datasetId=SKY&maxSize=1500&requestorId=<uuid>`, заголовок `ET-Client-Name: <app-name>` | Берген: 422 машины, 597 КБ; вся страна: 1 495 машин одним запросом, 3,4 МБ, 2,6 с. Инкрементально (тот же `requestorId`) раз в 10 с: ~570–650 изменённых записей, ~1,8 МБ | **Второй город.** XML-стандарт, дельта-синхронизация, потоковый разбор |
| **Entur Vehicles GraphQL** (альтернатива) | `POST https://api.entur.io/realtime/v2/vehicles/graphql`; подписка `wss://api.entur.io/realtime/v2/vehicles/subscriptions` (протокол `graphql-transport-ws`) | Запрос: 1 598 машин, 490 КБ JSON, 1,3 с. Подписка: ~208 обновлений/с по стране | Сравнение push vs pull в ADR; запасной канал |
| **MBTA GTFS-RT** (Бостон) | protobuf: `https://cdn.mbta.com/realtime/VehiclePositions.pb`, `.../TripUpdates.pb`, `.../Alerts.pb`; статика GTFS MBTA | 514 машин, возраст фида 5 с; покрытие: курс 81%, загруженность 72%, вагоны 12%; 1 232 Trip Updates; 159 Alerts | **Третий город.** Мировой стандарт GTFS-RT |

**Поля HFP-сообщения** (из реального сэмпла):
```json
{"VP": {"desi":"9","dir":"1","oper":40,"veh":415,"tst":"2026-10-02T19:10:52.101Z","tsi":1790968252,
        "spd":8.03,"hdg":254,"lat":60.202731,"long":24.924969,"acc":0.89,"dl":-195,"odo":9328,
        "drst":0,"oday":"2026-10-02","jrn":1912,"line":39,"start":"21:31","loc":"GPS",
        "stop":null,"route":"1009","occu":0}}
```
`spd` — скорость (м/с), `hdg` — курс, `dl` — отклонение от расписания (с), `odo` — одометр, `drst` — двери, `occu` — загруженность, `oper`+`veh` — уникальный идентификатор машины. Структура топика содержит режим транспорта, оператора, номер машины, маршрут, направление, время старта рейса, следующую остановку и геохэш.

**Поля SIRI-VM** (`MonitoredVehicleJourney`, из реального ответа Бергена): `LineRef` (`SKY:Line:6`), `DatedVehicleJourneyRef` (рейс), `VehicleMode`, `PublishedLineName`, `OperatorRef`, `OriginRef/OriginName`, `DestinationRef/DestinationName`, `Monitored`, `InCongestion`, `VehicleLocation` (`Latitude`/`Longitude`), `Bearing`, `Occupancy` (`seatsAvailable`…), `Delay` (ISO 8601 duration, `PT5M43S`), `VehicleStatus`, `VehicleRef`, `MonitoredCall` (`StopPointRef`, `Order`, `StopPointName`, `VehicleAtStop`), `RecordedAtTime` (время замера). Особенности: у части записей нет `VehicleMode`; данные менее свежие (медиана возраста записи ~40 с) — адаптер должен отбрасывать устаревшие записи по `RecordedAtTime`.

**Поля MBTA GTFS-RT `VehiclePosition`:** `trip` (trip_id, route_id, direction_id, start_time/date), `position` (lat, lon, bearing, редко speed), `current_stop_sequence`, `current_status` (`STOPPED_AT`, `IN_TRANSIT_TO`, `INCOMING_AT`), `stop_id`, `timestamp`, `vehicle` (id, label), `occupancy_status`, `occupancy_percentage`, `multi_carriage_details` (загрузка по вагонам). Задержки в позициях нет; в `TripUpdates` MBTA тоже нет поля `delay` — только абсолютные прогнозы `arrival.time` (замер 26.10.2026: 0 из 1,83 млн), поэтому задержку считает Processor по расписанию (`stop_times.txt`).

| Требование | Значение |
|---|---|
| Пропускная способность | Живой поток ~750+ сообщ./с (HSL) + Берген + Бостон; запас по дизайну до 5 000/с |
| Задержка источник → карта | p95 < 2 с |
| Доставка | At-least-once на чтении + идемпотентные приёмники; потерь нет, дублей на выходе нет |
| Доступность | 24/7, автоперезапуск, переподключение к источникам |
| Ресурсы | Один VPS, горизонтальное масштабирование без переписывания |

**Оценка объёма:** 1 000 сообщ./с × 86 400 с ≈ **86 млн позиций в сутки**. Хранить всё в Postgres на VPS дорого → многоуровневое хранение (раздел 6.5): прореживание до 1 точки / 10 с на машину (~8,6 млн строк/сутки со сжатием TimescaleDB), полный поток — в сжатых Parquet-файлах.

### 5.1. Бюджет и экономия инфраструктуры

Проект — пет-проект, расходы должны быть минимальными. Принцип: **на сервере круглосуточно работает только то, что нельзя остановить без потерь**, всё остальное — локально или по требованию.

**Замер объёма (октябрь 2026):** полный поток HSL ~730 сообщ./с × ~390 байт = ~25 ГБ/сутки в сыром виде; gzip — ~3,3 ГБ/сутки; **Parquet + zstd — ~1,4 ГБ/сутки** (вечерний темп; днём больше, ориентир 2–3 ГБ/сутки); при прореживании до 1 точки / 10 с на машину — ~0,14 ГБ/сутки. Хранить полный поток месяцами на дешёвом VPS нельзя.

**Двухфазная схема:**

| Фаза | Когда | Что на VPS | Что локально | Ориентир ресурсов |
|---|---|---|---|---|
| **A. Разработка** | Этапы 0–7 | Только **сборщик** (Ingestor в «режиме архива») + запись Parquet. Без Kafka/Postgres/Redis | Весь стек (Aspire), разработка, обучение ML | Самый дешёвый VPS: 1 vCPU, 1–2 ГБ RAM, 25–40 ГБ диск |
| **B. Демо** | С этапа 8 | Полный стек в docker compose: Ingestor, Processor, API, Worker, Redpanda (1 ГБ), Postgres+Timescale, Redis, Caddy, облегчённый мониторинг | Нагрузочные тесты, полная наблюдаемость (Tempo/Loki), обучение ML | 2 vCPU, 4 ГБ RAM, 40–80 ГБ диск |

Конкретного провайдера и цену выбирает автор (доступность оплаты, цена); стоимость фазы A должна быть минимальной из доступных тарифов, фаза B — порядка недорогого тарифа на 4 ГБ.

**Политика хранения на VPS:**
- **Полный сырой поток** — скользящее окно **3–5 дней** (для replay и отладки), затем удаляется.
- **Для ML** — сохраняются навсегда: события прибытия/отправления (крошечные), прореженные позиции (1 точка / 10 с), официальные прогнозы, погода, объявления. Это ~0,2–0,3 ГБ/сутки на все города.
- **Ежедневная выгрузка на локальный ПК** (скрипт по расписанию забирает файлы с VPS; окно 3–5 дней на VPS страхует, если ПК был выключен). На ПК хранится **вся история полного потока** (~40–90 ГБ/мес по трём городам — дешёвый локальный диск), пока Processor (этап 2) не научится извлекать из неё события; после этого полный поток можно сократить до «золотых дней» для replay-тестов.
- Алерт при заполнении диска > 80%.

**Другие меры экономии:**
- docker compose вместо k3s в продакшене; Kubernetes — Helm-чарты, проверяемые в CI на kind (бесплатно).
- Redpanda с лимитом памяти; лимиты памяти всех контейнеров.
- Фронтенд — статические файлы, раздаёт Caddy на том же VPS.
- Обучение ML — только на локальном ПК; на сервер попадает готовый файл модели (`.onnx`, единицы МБ).
- LLM: недорогая модель для простых задач, кэш ответов, лимиты на пользователя, **жёсткий дневной бюджет** с отключением ассистента при превышении.
- Наблюдаемость в продакшене облегчённая; полный стек — локально.
- Для «тяжёлых» сценариев (нагрузка ×50, полный трейсинг) — записанные результаты, графики и видео в README, а не постоянно работающая инфраструктура.

## 6. Архитектура

### 6.1. Общая схема

```
Источники: HSL MQTT JSON (push) · Entur SIRI-VM XML (инкрементальный pull) · MBTA GTFS-RT (pull)
           · расписания GTFS/NeTEx · официальные прогнозы и объявления · погода/события/дороги
        │
        ▼
┌──────────────────────┐
│ Ingestor              │ адаптер на источник → единая модель, дедуп, backpressure,
│ (.NET 10, Native AOT) │ архив сырого потока (replay)
└──────────┬───────────┘
           ▼  Kafka API (Redpanda) — topic positions.raw, ключ = vehicleId
┌──────────────────────┐
│ Processor (stateful)  │ трек → map matching → прибытие/отправление, задержка,
│                       │ слипание, стоянки; состояние в памяти + снапшот в Redis
└──┬─────────┬─────────┘
   │ positions.enriched   events.stop / events.anomaly
   ▼                      ▼
┌──────────────────────────────────────────────┐
│ Worker: запись в Timescale/Parquet, алерты,    │
│ детектор инцидентов, задачи обучения/отчётов   │
└──────────────────────────────────────────────┘
┌──────────────────────────────────────────────┐
│ API: REST (Minimal APIs) + SignalR + gRPC      │
│ модуль Prediction (ONNX) · модуль AI (ассистент,│
│ сводки) · MCP-сервер                           │
└──────────────┬───────────────────────────────┘
               ▼
 React + MapLibre · Telegram-бот · AI-агенты (MCP)
Всё: OpenTelemetry → Prometheus / Grafana / Tempo / Loki
```

**Деплоймент-единиц четыре:** Ingestor, Processor, API, Worker. Внутри — модульный монолит с чёткими границами (Domain без зависимостей, Infrastructure отдельно). Выделение нового сервиса — только с ADR, когда у модуля появляется собственная причина масштабироваться.

### 6.2. Ingestor

- Доставка и формат разделены: `IFeedSource` получает байты по протоколу, `IPositionNormalizer` города приводит их к единой модели:
  - `HslMqttSource` — push: постоянная MQTT-подписка, JSON, ~1 сообщ./с на машину; формат разбирает `HslPositionNormalizer`.
  - `HttpPollingSource` — pull любых HTTP-фидов: `ETag`/`If-Modified-Since`, ответ 304 или тело, совпавшее с прошлым, не архивируется; для Entur — постоянный `requestorId` (инкрементальный режим, в ответе только изменения), новый id после рестарта возвращает полный снимок.
  - `SiriVmPositionNormalizer` (Берген): **потоковый разбор XML через `XmlReader`** (ответы до нескольких МБ не держим целиком в памяти), парсинг ISO 8601 duration (`PT5M43S`), отбрасывание устаревших записей по `RecordedAtTime`.
  - `GtfsRtPositionNormalizer` (Бостон; общий для любого GTFS-RT-фида): полный protobuf-снимок; отдельной дельты снимков нет — машину без нового `timestamp` отсекает дедуп по `ObservedAt`; задержки адаптер не даёт (`null`) — её считает Processor.
  - Новый город = новый нормализатор (+ конфигурация), город на GTFS-RT — только конфигурация; остальная система не меняется.
- Нормализация различий: идентификаторы (`oper/veh` vs `VehicleRef` vs `vehicle.id`), единицы скорости, формат задержки, словари загруженности (HSL `occu` / SIRI `Occupancy` / GTFS `OccupancyStatus`) → единый enum, часовые пояса → `DateTimeOffset` UTC.
- Единая модель:
  ```csharp
  public sealed record VehiclePosition(
      string FeedId, string VehicleId, string? TripId, string? RouteId,
      double Lat, double Lon, float? SpeedMps, float? Bearing,
      int? DelaySec, OccupancyLevel? Occupancy, DateTimeOffset ObservedAt);
  ```
- Ограниченный `Channel<T>` между приёмом и продюсером → backpressure.
- Батчинг продюсера (`linger.ms`, сжатие lz4/zstd), идемпотентный продюсер.
- Дедуп по `(VehicleId, ObservedAt)`.
- Переподключение с экспоненциальной задержкой (собственный backoff без прозрачных ретраев, ADR-0007), метрика «секунд без данных» по источнику.
- **Архив сырого потока** по часам (сжатые файлы) → инструмент **replay** (проигрывание с множителем ×1…×50) для нагрузочных и регрессионных тестов.
- Сборка Native AOT: быстрый старт, малый размер, низкое потребление памяти на маленьком VPS.

### 6.3. Kafka-топики

| Топик | Ключ | Партиций | Retention | Назначение |
|---|---|---|---|---|
| `positions.raw` | vehicleId | 12 | 24 ч | Нормализованные позиции |
| `positions.enriched` | vehicleId | 12 | 24 ч | + маршрут, задержка, следующая остановка |
| `events.stop` | routeId | 6 | 7 д | Прибытия/отправления |
| `events.anomaly` | routeId | 3 | 7 д | Слипание, стоянки, всплески задержек, инциденты |
| `*.dlq` | — | 1 | 7 д | Необработанные сообщения |

Ключ `vehicleId` гарантирует порядок событий одной машины в одной партиции. Масштабирование — экземпляры в consumer group.

### 6.4. Processor (ядро)

1. Состояние машины (последние N точек) в памяти, снапшот в Redis для восстановления после ребаланса.
2. **Map matching**: проекция GPS на геометрию маршрута (`shapes.txt`), фильтрация шума, пройденная дистанция вдоль маршрута.
3. **Детекция прибытия/отправления**: вход в радиус остановки + скорость ≈ 0 + выезд → событие с фактическим временем.
4. **Задержка**: у HSL — поле `dl`, у Бергена — `Delay`, у Бостона — факт против `stop_times.txt` (в `TripUpdates` MBTA нет `delay`). Разные источники задержки — аргумент за единую модель; для контроля качества задержка дополнительно пересчитывается по расписанию во всех городах.
5. **Слипание**: по линии — упорядоченный список машин по дистанции; интервал < X% планового → событие.
6. **Гарантии**: детерминированные id событий (`vehicleId+tripId+stopId+serviceDate`), upsert; после N ретраев — в DLQ. Exactly-once Kafka-транзакции сознательно не используем (ADR).

### 6.5. Хранение

| Слой | Технология | Данные |
|---|---|---|
| Горячий | Redis | Текущие позиции (`GEOADD`/`GEOSEARCH`), состояние Processor, кэш прогнозов, pub/sub, дедуп алертов |
| Тёплый | PostgreSQL + TimescaleDB + PostGIS | Прореженные позиции (hypertable, сжатие, retention), события, инциденты, GTFS-справочник, continuous aggregates пунктуальности |
| Холодный | Parquet (локально → S3-совместимое) | Полный сырой поток для ML и replay |

### 6.6. API и доставка на карту

- REST на Minimal APIs, версионирование, OpenAPI.
- **SignalR**: клиент подписывается на видимую область/линию; сервер раз в 1 с шлёт **дельту только по видимым машинам** (иначе браузер захлебнётся). Redis backplane.
- **gRPC** — внутренний вызов Prediction.
- `HybridCache` (L1 память + L2 Redis, защита от stampede).
- Rate limiting (особенно AI-эндпоинты).

### 6.7. ИИ-слой

**ML — прогноз прибытия (ETA):**
- Данные: Parquet-история + события прибытия + погода/праздники/события.
- Признаки: оставшаяся дистанция, текущая задержка, задержки впереди идущих машин линии, час, день недели, праздник, погода.
- Обучение: Python (LightGBM) в `ml/`, экспорт в **ONNX**, инференс в .NET через `Microsoft.ML.OnnxRuntime` (< 1 мс).
- Метрика: MAE против (а) baseline «расписание + текущая задержка», (б) **официального прогноза перевозчика** в каждом городе (HSL и MBTA — GTFS-RT Trip Updates, Entur — SIRI-ET).
- Модель обучается на общих признаках для трёх городов (+ признак города); отдельно оценивается перенос на город, данных которого не было в обучении.
- MLOps-минимум: версия модели в каждом прогнозе, онлайн-сверка прогноза с фактом, алерт деградации.
- **Подробно — §6.11.**

**Детектор инцидентов:** правила + статистика (z-score задержки на участке относительно нормы для участка/часа, корреляция по нескольким линиям в одной точке), подтверждение дорожными сообщениями Digitraffic.

**LLM:**
- Ассистент на `Microsoft.Extensions.AI` с tool calling: `FindStops`, `GetArrivals`, `GetRouteDelays`, `GetIncidents`, `GetServiceAlerts`. Модель только выбирает инструменты и формулирует ответ.
- **«Почему опаздывает»**: сбор фактов (погода, ДТП на маршруте, событие рядом, объявление HSL) → одна понятная фраза.
- Пересказ/перевод официальных объявлений (fi → ru/en).
- Сводки инцидентов и ежедневный отчёт.
- **MCP-сервер** (официальный C# SDK) с теми же инструментами.
- Защита: лимиты на пользователя, кэш одинаковых вопросов, бюджет токенов, метрика стоимости.

### 6.8. Алерты

Подписки в Telegram (линия, остановка, дни, окно времени, порог задержки). Бизнес-логика бота отделена от транспорта мессенджера (интерфейс `IMessengerChannel`), чтобы при необходимости подключить другой мессенджер без изменения логики. Дедуп через Redis `SET NX` + TTL. Вебхуки — outbox-паттерн, ретраи с backoff, подпись HMAC.

### 6.9. Наблюдаемость

OpenTelemetry (трейсы, метрики, логи) во всех сервисах. Ключевые метрики: входящий поток по источникам, lag консьюмеров, задержка источник→карта p50/p95/p99, DLQ, MAE модели онлайн, стоимость LLM/сутки. Стек: Prometheus + Grafana + Tempo + Loki (в разработке — .NET Aspire Dashboard). Публичный дашборд «здоровья».

### 6.10. Деплой

- Локально: **.NET Aspire** AppHost (все сервисы и зависимости одной командой).
- Брокер: **Redpanda** (Kafka API, без JVM; в продакшене `--smp 1 --memory 1G`); код — на `Confluent.Kafka`.
- Продакшен: **один VPS + docker compose** (не k3s — экономия ~0,5–1 ГБ RAM), Caddy с автоматическим HTTPS, бэкапы Postgres. Фронтенд — статика, раздаётся тем же Caddy.
- Kubernetes: Helm-чарты в `deploy/helm`, проверяются в CI на временном кластере **kind** (бесплатно) и локально в k3d. Опыт с k8s подтверждается без оплаты отдельного сервера.
- Наблюдаемость в продакшене — облегчённая (Prometheus с коротким хранением + Grafana, либо бесплатный тариф Grafana Cloud, если доступен); полный стек (Tempo, Loki) — локально, для скриншотов и разборов.
- CI/CD: GitHub Actions — сборка, тесты (Testcontainers), образы, деплой по тегу.

### 6.11. Как обучается ИИ (подробно)

В проекте **два разных вида ИИ**, и учатся они по-разному:

| | ML-модель прогноза прибытия | LLM (ассистент, объяснения) |
|---|---|---|
| Что это | Своя модель, обучаемая на собственных данных | Готовая большая языковая модель через API |
| Обучается ли в проекте | **Да**, с нуля, на истории поездок | **Нет.** Мы её не обучаем и не дообучаем |
| Как становится «умной» под задачу | Обучение на примерах «ситуация → фактическое время в пути» | Инструкции (системный промпт) + инструменты (tool calling) с нашими данными |
| Где работает | Внутри .NET-сервиса (ONNX), бесплатно, < 1 мс | У провайдера LLM, платно за запрос |

#### A. ML-модель прогноза прибытия — полный цикл

**1. Сбор сырья (этап 1, непрерывно).** Позиции машин, официальные прогнозы, погода, праздники, объявления — архив Parquet (§5.1).

**2. Получение «правильных ответов» (меток).** Модель учится на примерах, где известен правильный ответ. Правильный ответ — **фактическое время прибытия** машины на остановку. Его даёт Processor (этап 2): событие `StopArrival` фиксирует, когда машина реально приехала на каждую остановку. Без надёжной детекции прибытия обучать нечего — поэтому этап 2 критичен для ML.

**3. Построение обучающих примеров.** Берём исторический момент: «в 08:12:30 автобус 55 (рейс X) находился в точке P, до остановки S оставалось 2,4 км, задержка была +3 мин». Правильный ответ: «он приехал на S в 08:19:10» → время в пути **400 с**. Из каждого момента поездки и каждой следующей остановки (на горизонте до ~30 мин) получается пример. За неделю по трём городам — **миллионы примеров**.

**4. Признаки (что модель «видит»):**
- **Положение:** оставшаяся дистанция по маршруту, число остановок до цели, тип участка.
- **Состояние сейчас:** текущая задержка, скорость за последние минуты, стоит ли машина.
- **Соседи:** задержки и скорость впереди идущих машин этой же линии и других линий на этом участке (лучший индикатор пробки впереди).
- **Время:** час, день недели, праздник, школьные каникулы.
- **Контекст:** осадки, снег, температура; событие рядом (для Хельсинки); «в пробке» (`InCongestion`, Берген).
- **Справочное:** линия, остановка, город, вид транспорта, плановое время в пути по расписанию.

**5. Baseline — с чем сравниваем.**
- (а) «Расписание + текущая задержка» — простая формула, её делает любое табло.
- (б) Официальный прогноз перевозчика (HSL/MBTA Trip Updates, Entur SIRI-ET) — сохраняем в момент прогноза и потом сверяем с фактом.
- Модель имеет смысл, только если она лучше (а); сравнение с (б) публикуется честно, даже если где-то проигрываем.

**6. Разбиение данных — без «подглядывания в будущее».** Только **по времени**: обучение на неделях 1–3, проверка на неделе 4. Случайное перемешивание даст завышенную точность: модель «увидит» соседние моменты той же поездки. Это частая ошибка в задачах на временных рядах.

**7. Обучение.** LightGBM (градиентный бустинг деревьев решений): быстро обучается на табличных данных, на обычном ПК — минуты, хорошо работает с пропусками и категориями, легко экспортируется в ONNX. Подбор гиперпараметров — небольшой поиск на валидационной неделе. **Нейросети не нужны**: для табличных данных бустинг обычно сильнее и намного проще.

**8. Оценка.**
- **MAE** (средняя ошибка в секундах) по горизонтам: 0–2, 2–5, 5–10, 10–20, 20–30 мин; по городам; по видам транспорта; в час пик и вне его.
- Доля прогнозов с ошибкой < 1 мин.
- Таблица: модель vs baseline (а) vs официальный (б). Это главный артефакт для README.
- Важность признаков: какие факторы сильнее всего влияют (материал для README и статьи).

**9. Экспорт и внедрение.** Модель → файл `.onnx` (единицы МБ) → загружается в .NET-сервис через `Microsoft.ML.OnnxRuntime`. Признаки в продакшене считаются **тем же кодом**, что и при обучении (общая спецификация признаков + тест на совпадение), иначе модель будет работать хуже, чем на проверке (training–serving skew).

**10. Работа в продакшене и контроль качества.** Каждый прогноз сохраняется с версией модели; когда машина реально приезжает, прогноз сверяется с фактом → онлайн-MAE на дашборде. Если ошибка выросла (сменилось расписание, пришла зима) — алерт.

**11. Переобучение.** Раз в 1–2 недели на локальном ПК: свежие данные → обучение → сравнение с текущей моделью на одной и той же проверочной неделе → если лучше, новый `.onnx` выкатывается на сервер. Сервер не тратит ресурсы на обучение.

**Ноутбуки:** Jupyter-ноутбуки в `ml/` с пошаговым разбором — загрузка данных, построение примеров, признаки, обучение, графики ошибок, важность признаков.

#### B. LLM — не обучаем, а «оснащаем»

- **Системный промпт:** роль («помощник по транспорту города X»), правила («отвечай только на основе данных инструментов; если данных нет — так и скажи»), язык ответа.
- **Инструменты (tool calling):** модель получает описание функций (`FindStops`, `GetArrivals`, `GetRouteDelays`, `GetIncidents`, `GetServiceAlerts`), сама решает, какие вызвать, получает **наши реальные данные** и формулирует ответ. Знания модели о расписаниях не используются.
- **Проверка качества:** набор из 20–30 эталонных вопросов (eval-набор); при каждом изменении промпта/инструментов прогоняем набор и проверяем, что ответы опираются на вызовы инструментов, а не на «фантазию».
- **Почему не дообучаем LLM:** дорого, не нужно (данные меняются каждую секунду — их всё равно надо подставлять в реальном времени), и tool calling решает задачу надёжнее.

## 8. ADR для написания (`docs/adr/`)

1. Модульный монолит + 4 деплоймент-единицы вместо микросервисов.
2. Redpanda вместо Apache Kafka на VPS.
3. Ключ партиционирования `vehicleId` и порядок событий.
4. At-least-once + идемпотентные приёмники вместо exactly-once.
5. Многоуровневое хранение и прореживание позиций.
6. Единая модель `VehiclePosition` и паттерн адаптера источников (три формата, три протокола).
6a. Push vs pull: MQTT (HSL), инкрементальный SIRI-опрос (Entur) против GraphQL-подписки Entur, полный GTFS-RT-опрос (MBTA) — почему выбран каждый вариант.
7. SignalR: дельты по видимой области вместо широковещания.
8. Обучение на Python, инференс ONNX в .NET.
9. LLM только через tool calling (запрет «знаний модели» о расписаниях).
10. Стратегия тестирования (replay-тесты как регрессия).
11. Observability: что измеряем и почему.
12. Деплой: docker compose на одном VPS + Helm-чарты, проверяемые в CI (почему не k3s в продакшене — бюджет).

Формат ADR: контекст, решение, рассмотренные альтернативы, последствия. До 1 страницы.

## 10. План работ

**Принципы планирования:**
- Порядок этапов подчинён целям: сначала то, что **нельзя наверстать** (сбор истории), затем то, что даёт **первое демо** (неделя 4), затем то, что делает систему зрелой (надёжность, нагрузка, ML, наблюдаемость).
- Каждый этап заканчивается работающим, задеплоенным (хотя бы локально) состоянием и записью в README/ADR.
- У этапа есть критерии приёмки; этап не закрыт, пока они не выполнены.

### Этап 0. Фундамент (2–3 дня)
**Цели:** C1, C9, C11.
- Публичный репозиторий, лицензия (MIT), структура из раздела 9, `.editorconfig`, анализаторы, `Directory.Build.props`, `TreatWarningsAsErrors`.
- .NET Aspire AppHost: Redpanda, Postgres+Timescale+PostGIS, Redis.
- CI: build + test на каждый PR; шаблон PR; GitHub Project с milestones = этапы.
- Настроить работу с Claude Code (§11.3): `docs/STATUS.md`, `docs/stages/`, `docs/adr/` (шаблон), hooks, skills, subagents.
- Выбрать дешёвый VPS для фазы A (§5.1) и запустить на нём сборщик сразу после этапа 1 (п. 1).
- Проверить лицензии/условия HSL, Entur, MBTA и Digitraffic, записать атрибуцию.

**Приёмка:** `dotnet run` в AppHost поднимает инфраструктуру; CI зелёный; первый PR влит через ревью-процесс.

### Этап 1. Сбор данных трёх городов (неделя 1–1,5) — ЗАПУСТИТЬ КАК МОЖНО РАНЬШЕ
**Цели:** C1, C2 (начало), C2a, C5 (данные для обучения).

Все три адаптера делаются сразу: история нужна для ML во всех городах, а разнообразие форматов — ключевая проверка архитектуры (C2a). Порядок внутри этапа — от простого к сложному, чтобы сбор стартовал в первый же день:

1. **День 1–2:** «сырые сборщики» для всех трёх источников — сохраняют ответы как есть в архив по часам (MQTT-сообщения HSL; XML-ответы Entur; protobuf-снимки MBTA). Запуск на **дешёвом VPS фазы A** (§5.1) сразу — **с этого момента копится история**. Политика хранения §5.1: полный поток — скользящее окно 3–5 дней, для ML — прореженные данные и события; ежедневная выгрузка на локальный ПК.
2. **День 3–5:** полноценные адаптеры с нормализацией в `VehiclePosition` → `positions.raw`:
   - `HslMqttSource` (MQTT JSON, push);
   - `SiriVmPollingSource` (SIRI XML, инкрементальный `requestorId`, `XmlReader`, ISO 8601 duration, отсев устаревших записей);
   - `GtfsRtPollingSource` (protobuf, `ETag`, дельта снимков).
3. **День 5–7:** сбор вспомогательных данных в архив: официальные прогнозы (HSL Trip Updates, Entur SIRI-ET, MBTA Trip Updates), объявления (GTFS-RT Alerts, SIRI-SX), погода Open-Meteo для трёх городов.
4. Общие механизмы: метрики входящего потока по источнику, переподключение/ретраи (ADR-0007), дедуп, тревога «источник молчит».
5. Инструмент replay (×1…×50) для любого источника.

Контрактные тесты адаптеров: на сохранённых реальных ответах каждого формата (JSON, XML, protobuf) проверяется корректная нормализация.

**Приёмка:** на VPS круглосуточно копится история всех трёх городов (сырьё + вспомогательные данные); все три адаптера пишут в `positions.raw` единую модель; замерен суточный профиль потока по каждому городу; replay воспроизводит записанный час; контрактные тесты зелёные.

## 11. Рабочий процесс

### 11.1. Командный процесс (цель C11)

- **GitHub Projects**: issues с критериями приёмки, milestones = этапы, лейблы (`domain`, `infra`, `ml`, `ai`, `web`, `perf`).
- **Ветки и PR**: `feature/<issue>-<slug>`, PR с описанием «что / зачем / как проверить / скриншоты», самопроверка по чек-листу, squash-merge.
- **Conventional commits**: `feat(processor): detect stop arrivals`.
- **CI обязателен**: красный CI не мержится.
- **ADR** на каждое решение, которое можно оспорить.
- **Changelog / release notes** на каждый этап (тег `v0.N`).
- **Еженедельный прогресс**: короткая запись в `docs/progress.md` (что сделано, что узнал, проблемы) — материал для статьи.

### 11.2. Размер изменений и комментарии

1. **Маленькие шаги.** Один шаг — один логический кусок (обычно 1–3 файла, до ~150 строк изменений), который легко отревьюить.
2. **Перед кодом — план:** что делаем, зачем (связь с целью брифа), какие файлы меняются, рассмотренные варианты и почему выбран этот.
3. **Комментарии в коде:** XML-doc на публичных типах и методах (что и зачем); внутри — комментарии только к неочевидному «почему», а не к очевидному «что».

### 11.3. Разработка с ИИ-ассистентом (Claude Code)

**Принцип:** контекст для ассистента хранится в репозитории, рядом с кодом (бриф, ADR, спецификации этапов, PR). Это одновременно память ассистента и документация инженерного процесса.

**Слои контекста:**

| Слой | Файл | Что содержит | Как меняется |
|---|---|---|---|
| Конституция | `PROJECT_BRIEF.md` | Цели, ограничения, архитектура, план | Редко, по решению автора |
| Правила | `CLAUDE.md` (корень) | Ключевые правила работы, ссылки | Редко |
| Локальные правила | `src/<Project>/CLAUDE.md` | Неочевидные правила модуля («SIRI — только `XmlReader`», «Domain без зависимостей») — подгружаются, только когда работа идёт в этой папке | При появлении правила |
| Решения | `docs/adr/NNNN-*.md` | Почему выбрано X, альтернативы | Новый ADR на каждое спорное решение |
| План этапа | `docs/stages/stage-N.md` | Цель, задачи с чекбоксами, критерии приёмки, ссылки на ADR | Пишется в начале этапа, чекбоксы — по ходу |
| Состояние | `docs/STATUS.md` | Текущий этап, что сделано, что в работе, проблемы, следующий шаг | В конце каждой сессии |

Project map не ведётся вручную: понятная структура репозитория + локальные `CLAUDE.md` дают ту же навигацию без риска устаревания.

**Цикл работы:**

1. **Начало сессии:** ассистент читает `CLAUDE.md` → `docs/STATUS.md` → `docs/stages/stage-N.md` и кратко пересказывает, где мы и что дальше.
2. **Новый этап:** в plan mode совместно пишется `docs/stages/stage-N.md` (spec-driven): задачи, критерии приёмки, риски, нужные ADR. Задачи → GitHub issues.
3. **Задача:** plan mode → автор утверждает план → код маленьким шагом → hooks собирают и тестируют → автор проверяет изменения → следующий шаг.
4. **Перед PR:** сабагент-ревьюер проверяет изменения по брифу, ADR и локальным правилам; замечания исправляются; PR с описанием.
5. **Конец сессии:** обновление `STATUS.md` и чекбоксов в `stage-N.md`.
6. **Конец этапа:** проверка критериев приёмки, README, тег `v0.N`, запись в `docs/progress.md`.

**Автоматизация Claude Code (настраивается на этапе 0):**
- **Hooks** (`.claude/settings.json`): после правок `.cs` — `dotnet build` затронутого проекта; после правок тестов — запуск этих тестов; перед коммитом — `dotnet format --verify-no-changes`. Ассистент физически не может «забыть» проверить сборку.
- **Skills** (`.claude/skills/`):
  - `new-adapter` — чек-лист подключения источника данных (адаптер, нормализация, контрактные тесты на сохранённых ответах, метрики, конфигурация, документация);
  - `new-adr` — шаблон и правила ADR;
  - `start-stage` / `close-stage` — открытие этапа (спецификация, issues) и закрытие (критерии приёмки, README, тег);
- **Subagents** (`.claude/agents/`):
  - `reviewer` — ревью изменений по брифу, ADR и локальным правилам (имитация командного код-ревью);
  - `test-writer` — предлагает тесты, особенно граничные случаи;
- **Permissions:** разрешить без подтверждения безопасные команды (`dotnet build/test/format`, `git status/diff/log`), всё остальное — с подтверждением.

## Приложение B. Глоссарий

- **GTFS** — стандарт расписаний общественного транспорта (маршруты, остановки, рейсы, геометрия).
- **GTFS-Realtime (GTFS-RT)** — стандарт данных реального времени (позиции, прогнозы, объявления) в protobuf.
- **HFP** — High-Frequency Positioning, MQTT-поток HSL с позициями раз в секунду.
- **SIRI** — Service Interface for Real-time Information, европейский стандарт данных реального времени (XML): **VM** — позиции машин (Vehicle Monitoring), **ET** — прогнозы по рейсам (Estimated Timetable), **SX** — объявления о сбоях (Situation Exchange).
- **NeTEx** — европейский стандарт расписаний (XML), аналог GTFS.
- **Entur** — национальный оператор транспортных данных Норвегии; **Skyss** — перевозчик Бергена (код `SKY`).
- **MBTA** — транспортная компания Бостона.
- **Метка (label)** — «правильный ответ» в обучающем примере ML; здесь — фактическое время прибытия.
- **Training–serving skew** — расхождение признаков при обучении и в продакшене, из-за которого модель работает хуже, чем на проверке.
- **Eval-набор** — фиксированный набор вопросов для проверки качества ответов LLM после изменений.
- **Map matching** — привязка GPS-точки к линии маршрута.
- **Слипание (bus bunching)** — машины одной линии идут вплотную, после них большой интервал.
- **Backpressure** — механизм притормаживания приёма при перегрузке обработки.
- **Idempotency** — повторная обработка не меняет результат.
- **DLQ** — очередь сообщений, которые не удалось обработать.
- **ADR** — Architecture Decision Record, короткая запись архитектурного решения.
- **MAE** — средняя абсолютная ошибка прогноза.
- **MCP** — Model Context Protocol, протокол подключения инструментов к AI-агентам.
